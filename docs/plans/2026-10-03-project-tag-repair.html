3. Repair design

Revised after outside review (2026-10-03). Principles: explicit operator intent is the evidence; dry run is the default; one BEGIN IMMEDIATE transaction per store; tenant-scoped; a database backup is written before any change and its path printed; one audit event records every id touched; nothing is deleted, removed rows go to dormant_memories through setAsideRow.

  1. hippo projects (read-only): each origin in the current store with live row counts (imported vs saved) and newest write. Hints: live worktrees come from git worktree list run in the current checkout, so they are exact. For other names the evidence is how many of their imported notes are copies held under another name, never a merge target. On Keith's store every old worktree name imported the same home-level notes folder, so a "shares notes with X" hint pointed at a sibling worktree and was dropped.
  2. hippo projects merge <from> <into> [--apply], for the resolved tenant:
    • '' and null are refused as either side; user-global and unknown are not projects.
    • Import rows of from (source agent-memory:<tool>:<container>/…, where the container hashes folder plus origin) are copies of note files. All of them are set aside with a new SetAsideWhy of 'project-merge'. The next sync under into re-imports every note still on disk under its own container, and a note no longer on disk was stale anyway. A pinned row comes back untagged rather than removed: restamp that result. This replaces the reviewer's prefix rewrite and same-scope text match: no folder has to be resolved, and no copy can survive under the wrong container.
    • Every other live row of from: restamp to into.
    • Rows outside memories that carry origin: dormant rows (entry_json) and compactions.origin_project are restamped too, so a later restore does not come back hidden.
    • After commit: purge mirrors of set-aside rows and rewrite mirrors of restamped rows, the same order sync.ts uses, or rebuildIndex brings old values back.
    • Undo: no command. The backup plus the audit event's ids are the undo path. A sleep after the merge can fold restamped rows into new merged rows, which no id list can reverse.
  3. hippo projects repair [--apply] (built as its own subcommand, so it does not hide behind a merge), for source='consolidation' rows stamped '': if their parents (live or dormant) agree on one project, stamp that project. If the parents disagree, set the row aside; the parents re-merge per project on the next sleep. Changed after a dry run on a copy of Keith's store: a row with no parent left is not touched. The reviewed plan restamped it null, which would have hidden 90 of the 91 rows from every project on no evidence; some are truly user-global.
  4. hippo doctor: one projects line, warning when repair would change a row (from the same read-only plan function). Never applies anything. Worktree names are listed by hippo projects, not by doctor.

Not automatic on upgrade. Default freeze applies, and a silent restamp across a fleet is the wrong default for enterprise. Admins can script merge per store from the projects output.

4. Mixed-version fleets

One docs line: upgrade every hippo on the machine (a second global install, a pinned plugin) and the server, server first, before running merge. An older binary keeps writing worktree names and cross-project merges until it is upgraded.

5. Open enterprise risk: project identity is the folder name

Two different repos cloned into folders with the same name (for example /workspace in agent sandboxes, or api in two orgs) share one origin in a shared store, so each sees the other's memories. Candidate fix: an explicit project id, taken in order from .hippo/project.json, else the normalised git remote URL (github.com/org/repo), else the folder name. Existing rows keep their old origin, so the switch needs an alias table (old name to new id, per store) or a projects merge run per checkout. Separate plan: 2026-10-03-project-identity.html; not in this change.
