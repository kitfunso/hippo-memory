A project identity that two repos cannot share

Status: revised 2026-10-04 after outside review; approved by Keith to build. The revision drops the alias table, so there is no schema change. Follows 2026-10-03-project-tag-repair.html section 5.

1. Problem

A memory's project is a folder name: resolveProjectIdentity (src/project-identity.ts) takes the basename of the nearest .hippo or .git folder, lowercased, or the repo's name for a linked worktree. Two different repos in folders with the same name get the same project. In the global store each then sees the other's memories in its ambient context, the memory hippo adds to every prompt unasked. It hits agent sandboxes that check every repo out to /workspace or /app, common names across teams (api, web, infra), and a fork cloned beside its upstream.

User-global ('') and unknown (null) keep their meaning; home and markerless folders stay user-global.

Normalising the remote. Strip userinfo (tokens), port, a trailing .git and /; lowercase; turn the scp form host:org/repo into host/org/repo, so ssh and https agree. Local-path and file:// remotes fall back to the folder name, since they would put user paths into rows. Azure DevOps ssh and https paths differ; normalise both to dev.azure.com/org/project/repo. Ignore include, includeIf and insteadOf: the raw URL is stable on one machine, and the file covers fleets. The parser handles quoted values, # and ; comments, and the case-sensitive subsection name. A linked worktree reads <commondir>/config; a submodule (a .git file with no commondir) reads <gitdir>/config.

Switch. On by default, with projectIdentity.remote: false in config as the off switch for one release. An opt-in reaches no fleet and would mean switching identity twice.

3. Existing rows: two names on read, a fold to finish

ProjectIdentity gains legacyName, today's folder rule, which costs nothing extra to compute. Every read that compares origin_project to the current project admits {id, legacyName}, so old rows stay exactly as visible as today and no new row leaks, since new rows carry the id. No table, no migration, no write from the prompt hook.

Read sites that take the two-name set: classifyOriginProject and its callers (context.ts, capture.ts, shared.ts), ambientSecretAdmit, invalidation.ts, and the SQL filters in ambient-store.ts, store/candidates.ts, agent-memories/sync.ts and compaction-record.ts. MCP and HTTP recall take the identity from the same resolver.

The permanent move is hippo projects repair: its fold step (planFolds) already folds a name whose every recorded folder resolves to one other project today, so api folds into github.com/acme/api. Where folders resolve to two ids it refuses, and that refusal is the collision report: doctor names the shared legacy name from the same plan. Sleep partitions (consolidation, DAG, dedupe) key on origin_project, so old and new rows only consolidate together after a fold.

Project stores. Only one repo writes a project store, so its legacy name cannot collide. The two-name read keeps its rows visible; repair in a project store folds the store's own legacy name into its id, which is safe there.

4. Agent-memory imports: adopt, never copy

In the global store's project pass the container id hashes folder plus origin (source.ts), so a new id is a new prefix and every note would import again; the duplicate check skips agent-memory sources, so nothing would catch it. Local stores hash the folder alone and need no change.

Fix: inside each container's transaction, when the new prefix holds no rows and the legacy prefix (containerId(path, scope, platform, legacyName)) does, rename the prefix on live rows and dormant snapshots and set the new origin; rewrite mirrors after commit. The folder path is in the hash, so two api checkouts each adopt only their own rows. legacyName joins the handover origins and the unlisted-rows partition. foldInTx uses the same prefix rename for imports instead of setting them aside, so a fold stops churning rows through dormant.

5. Rollout notes

  • An older binary sees id-tagged rows as another project's, so a downgrade hides them until upgrade. Release notes say so.
  • Doctor's projects check flags each upgraded global store until hippo projects repair --global runs; the warning names the fold.
  • Org and repo names appear in rows and audit events. They already appear in shared: sources and folder names, so this is no new class of data; the SIEM export docs say so.
  • hippo-enterprise reports that group by origin_project show the id after upgrade; check them before release.

6. Checks that close it

  • Identity matrix: file, ssh remote, scp form, https with a token and port, Azure DevOps both forms, file remote, no remote, worktree, submodule, bare repo, home, remote: false.
  • Two repos named api with different remotes, one global store: neither sees the other's new rows; old rows stay visible to each through the legacy name; repair refuses to fold api and doctor names it.
  • Upgrade: rows under the folder name stay visible; the agent-memory sync adopts the legacy container and creates no copies; dormant snapshots move with it.
  • Tests that resolve process.cwd() inside a checkout with an origin get the id; fixtures without a remote keep the folder name.
  • Per-prompt hook: one to three small file reads more, inside the existing p95 gate.
