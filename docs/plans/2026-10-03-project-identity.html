A project identity that two repos cannot share

Status: draft, 2026-10-03. Not built. It needs a schema change (a new table), so it needs Keith's yes before code. Follows 2026-10-03-project-tag-repair.html section 5.

1. Problem

A memory's project is a folder name: resolveProjectIdentity (src/project-identity.ts:96) takes the basename of the nearest .hippo or .git folder, lowercased, or the repo's name for a linked worktree. Two different repos in folders with the same name get the same project. In the global store, each then sees the other's memories in its ambient context. Ambient context is the memory hippo adds to every prompt without being asked. Cases this hits:

  • Agent sandboxes and dev containers that check every repo out to /workspace, /app or /src.
  • Common repo names across orgs or teams: api, web, infra, docs.
  • A fork and its upstream, cloned side by side under one name in two parent folders.

Tenants keep users and orgs apart; this is a leak inside one tenant's store. A project store (.hippo in the repo) does not have the problem, because only that repo writes to it.

3. Existing rows: an alias table, never a silent rewrite

  • New table project_aliases(tenant_id, legacy_name, project_id, first_seen). The first time a checkout resolves to an id whose folder-name form differs, hippo records legacy_name → project_id.
  • Ambient context treats rows tagged with a legacy name the table maps to the current id as the project's own. Old memories stay visible with no rewrite.
  • Collision detection: if a second, different id later claims the same legacy name, it gets no alias. hippo doctor then warns that two repos share the name, and new rows stop leaking from then on. Today the collision is silent.
  • An operator who wants the old rows moved for good runs hippo projects merge <legacy> <id> (already built), and the alias is then no longer needed.

4. Open design points

  • Agent-memory imports. The container id hashes folder plus project (source.ts:13), so a new id re-imports every note once. The sync should adopt rows of an aliased legacy container the way legacy.ts adopts old Claude imports, instead of creating copies. This must ship in the same change, or each user gets one more full set of duplicates.
  • Mixed fleets. An old binary keeps writing folder names. The alias covers reads, so the rollout order matters less than in the repair, but doctor should report rows written under a legacy name after the alias was recorded.
  • Remote changes. A repo moved to a new org gets a new id. The alias chain (old id to new id) uses the same table; project.json is the stable answer for teams that move repos.
  • Privacy. Org and repo names appear in rows and in audit events. They already appear in shared: sources and folder names, so this adds no new class of data, but the SIEM export docs should say so.

5. Checks that close it

  • Identity matrix tests: file, ssh remote, https remote with a token, no remote, worktree, bare repo, submodule, home.
  • Two repos named api with different remotes, one global store: neither sees the other's new rows in ambient context; doctor warns about the shared legacy name.
  • Upgrade test: rows under the folder name stay visible through the alias, and the agent-memory sync creates no copies.
  • Per-prompt hook latency stays within the existing p95 gate (one extra file read).
