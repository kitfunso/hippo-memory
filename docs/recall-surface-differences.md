# Recall surface differences

Recall has three surfaces: CLI `hippo recall` (`src/surface/cli/recall.ts`), MCP `hippo_recall` (`src/surface/mcp/recall-tools.ts`) and HTTP `GET /v1/memories` (`src/surface/server/routes/recall.ts`). Each enters `src/api/recall`: CLI through `retrieveWithCliCore` (`request.ts`), MCP through `retrieveRanking` and HTTP through `retrieve` (`recall.ts`). All three rank with one ranker, `rankRecall` (`src/api/recall/pipeline.ts`), under the profile their entry names: `BUDGET_RANKED` for CLI, `BAND_RANKED` for MCP and `POSITION_BAND` for HTTP (`src/api/recall/profiles.ts`). The profiles differ, so the same query on the same store gives a different answer on each one; D1 to D6 name the profile field behind each ranking difference. This file lists the 18 differences found in the code. Each one is asserted in `tests/store/recall-surface-differences.server.test.ts`; the test comments name the entries they assert (D1 to D18).

When a change closes a difference, update its entry and those asserts in the same PR, and add one changelog line for each surface whose output moves.

## Ranking

- **D1 Ranking core.** `scoreForm` and `scopeBoost`. CLI ranks under `BUDGET_RANKED` from `src/api/recall/request.ts`, for the host admin only; `hippo explain` uses the same profile read-only. MCP ranks under `BAND_RANKED` and hands the ranking to its `show` presenter. CLI and MCP have `scoreForm: 'engine'`: the search engine's list, physics by default. HTTP has `scoreForm: 'position'`: it keeps the SQL BM25 load order plus a churn sort, unless `mode` asks for hybrid or physics. With `scopeBoost: 'active'`, CLI and MCP boost the active scope; with `scopeBoost: 'filter'`, HTTP boosts the scope it filters on.
- **D2 Candidate window.** `candidateFloor`. CLI loads 200 rows per store (floor 0). MCP loads at least 1,000 rows (floor 1,000); `scorer_window` only shapes the fresh-tail and summary appendix. HTTP loads `scorer_window` rows, 200 by default (floor 0).
- **D3 Global store.** `globalReach`. Only CLI (`globalReach: true`) searches the global store (`HIPPO_HOME`), which the CLI passes as `sources` on its ranking request, and only that profile writes a `recall` audit row there.
- **D4 Scores.** `scoreForm`. HTTP (`'position'`) scores are list positions, `1 - idx / limit`, in every mode; `mode=hybrid` and `mode=physics` only reorder. CLI and MCP (`'engine'`) scores come from the search engine. MCP prints no score; its trace stores the engine score.
- **D5 Result count.** `resultCount`. CLI (`'budget'`) fits the token budget with no default limit. MCP and HTTP (`'band'`) rank every loaded row and cut from the band composed from that list: MCP ranks a 50-row band and shows what fits the budget; HTTP returns `limit` rows, 10 by default, and has no budget. CLI and MCP cut to the budget with one function, `fitRecall` (`src/api/recall/rows.ts`), each with its own row price and render.
- **D6 Goal boost.** `goalBoost.ranked` and `goalBoost.band`. CLI applies the goal-stack boost once, to the ranked list (`ranked` only). HTTP applies it once, to the position scores (`band` only). MCP applies it twice: to the ranked list, then again to the band's position scores (both).

## Side effects

- **D7 Strengthening and stats.** CLI strengthens the rows it shows, in the local and global stores, adds them to `total_recalled` and saves the last-recall markers `hippo outcome` reads; `retrieve` does all of it. HTTP strengthens every row it returns, and `retrieve` adds them to `total_recalled` because the route sets `recordAs`. MCP strengthens the rows it shows and never updates `total_recalled`. On every surface the audit rows go first, in one transaction with the goal log: a recall whose audit write fails leaves no strengthen, trace or count. HTTP and MCP then fail the call; CLI logs the failure and still prints. Recall and context keep the ids they return or show for the next `outcome` call that names none (`keepShownIds`, `src/api/recall/last-recalled.ts`), keyed by the `clientKey` the HTTP and MCP surfaces put on the context; CLI sets none and uses its markers.
- **D8 Audit count.** Closed. Every surface's `recall` audit row counts the rows it returns or shows. MCP used to count its 50-row band.
- **D9 Audit order and actor.** CLI writes `recall_anchor_skipped_no_session` before `recall`, as actor `cli`. HTTP writes them in the same order, as the key's subject. MCP writes `recall` first, as `mcp`.
- **D10 Trace and token ledger.** CLI traces with pipeline `cli`, MCP with `mcp` and HTTP with `api`. The ledger surfaces are `recall`, `mcp_recall` and `http_recall`; the MCP row records 0 items. The api books all three through `recordShownRecall` (`src/api/recall/finish.ts`): `retrieveWithCliCore` the CLI row, and `retrieve` and `retrieveRanking` the HTTP and MCP rows under `recordAs`.
- **D11 Session ring.** The rings sit on the `CallerState` each server, stdio MCP host and CLI command builds (`src/api/callers.ts`), one map per surface keyed by tenant and session; `src/api/recall/session-rings.ts` keeps them and `src/api/recall/finish.ts` writes the hint audit rows. Each surface keeps its own rings, so a repeat on one surface is a first recall on another. CLI and MCP create the ring before ranking and judge the hint against the list they show. HTTP has its ring created only after a successful recall and its hint judged against the first returned row. `recordShownRecall` feeds all three (`src/api/recall/finish.ts`).

## Validation, MCP against HTTP

Both surfaces now check recall and context inputs with `parseRecallRequest` and `parseContextRequest` (`src/api/recall/request.ts`). A bad input gets the same message on both: HTTP answers 400, MCP answers an `isError` result that starts `Invalid arguments for <tool>:`. The MCP input schema still rejects a wrong type first, with its own message.

- **D12 Empty query.** Closed. HTTP rejects with `q is required`, MCP with `query is required`.
- **D13 `scorer_window`.** Closed for the cap: both reject a value above 1,000. For 0, a negative or a non-number, both reject with `invalid_scorer_window`, which `retrieve()` raises: HTTP as a 400 with that code, MCP as a raw `RecallContractError` that the transport turns into a JSON-RPC error.
- **D14 `fresh_tail_count`.** Closed. Both reject a negative value.
- **D15 `fresh_tail_session_id`.** Closed. Both cap it at 256 characters.
- **D16 Surface-only arguments.** Both check `limit` and `mode` by the same rules, but MCP then ignores them: it ranks a 50-row band in the store's search mode. MCP has `budget` and rejects a negative one; HTTP ignores it. MCP's schema rejects a non-boolean `summarize_overflow`; HTTP reads any value other than `1` or `true` as false. Both cap `session_id` at 256 characters and treat a blank one as absent.
- **D17 Context.** Both cap `scope` at 256 characters and reject a negative `budget` and a `limit` of 0 or less, with the same messages. MCP `hippo_context` takes no query text: it reads the task from git, or none on a shared store, and it ignores `limit`. HTTP caps `q` at 1,024 characters; MCP applies the same cap to a `query` argument it then ignores. On a store whose `config.json` sets `"sharedStore": true`, HTTP needs the caller's `project` and answers 400 without it. MCP `hippo_context` over HTTP reads the project from the `X-Hippo-Project` header and returns an `isError` refusal without one; over stdio it always refuses and points to `hippo_recall` (pinned by `tests/store/shared-store-context.process.test.ts`).

## Shared store, MCP against HTTP

- **D18 Project filter.** On a store whose `config.json` sets `"sharedStore": true`, MCP `hippo_recall` over HTTP shows only the rows of the repo named in `X-Hippo-Project`, plus user-global ones, and refuses a call that names no repo. HTTP `GET /v1/memories` takes no project, so it returns every repo's rows in the tenant. Backlog item E15 adds a project to the HTTP recall routes.
