# Z0 analyzer: usage, record contract and readings

**Date:** 2026-10-03
**Implements:** the analysis section of `docs/evals/2026-09-29-z0-built-in-memory-prereg.md` (stage 2 commits and hashes, line 240). Line numbers below refer to that file.
**Code:** `scripts/token-eval/z0-records.mjs`, `z0-filters.mjs`, `z0-hypotheses.mjs`, `z0-gates.mjs`, `z0-blind.mjs`, `z0-analyze.mjs`. Statistics come from `src/eval-stats.ts` through `dist/eval-stats.js`.
**Tests:** `tests/token-eval-z0-analyze.test.ts` and `tests/token-eval-z0-analyze-cli.test.ts` on generated records (`tests/fixtures/z0-gen.ts`). Synthetic records test the contract, the filters and the arithmetic. They say nothing about hippo.

## Usage

```
npm run build
node scripts/token-eval/z0-analyze.mjs --runs FILE [--runs FILE ...] --plan FILE [--plan FILE ...] --prices FILE \
  [--grading FILE] [--drop-list FILE] [--key FILE] [--unblind] [--seed N --iterations N] [--out FILE]
node scripts/token-eval/z0-analyze.mjs --help
```

Exit 0 means a report was written, including for an invalid or abandoned run, or that `--help` printed the usage. Exit 1 means bad input: a malformed record, plan, prices, grading file or drop list, a key file made for another arm set, an `--out` path whose folder does not exist (checked before the key is written), or an unknown flag. Exit 2 means an unblind was refused.

**Order of work for a scored run:**
1. Run blind. The first blind run writes the key (`z0-blind-key.json` beside the first `--runs` file, or `--key FILE`) and prints per-code counts, the gates and the input hashes. It prints no outcome.
2. Re-grade and write the grading file. Decide the drop list. Commit both.
3. Run with `--unblind`. The run is refused (exit 2) when:
   - G5 fails;
   - `--drop-list` or `--grading` is missing, untracked, or has uncommitted changes;
   - `--iterations` or `--seed` is given;
   - the run is abandoned (prereg 114: never analysed, so its codes stay closed).

   An unblinded run always uses 10,000 resamples and seed 1 (189).

A blind run with other `--iterations` or `--seed` values is labelled "not of record". With every gate passing, the unblinded report prints names, descriptives, the hypothesis block and the reported block. With a failed gate it prints names, descriptives and the gates, and withholds the hypothesis block (156, 256).

The key is plaintext beside the records, so blindness is procedural. It keeps a reader from seeing arm outcomes by accident; it does not stop an operator who opens the key. The per-code planned counts also partly identify codes, since seed counts and set sizes differ by arm: a two-seed arm or a set X arm shows a smaller count. The arms inside each hypothesis pair (A1, A2 and A5; X2 and X3) have equal counts, so H1 to H3 stay blind.

**Status line.** Every report opens with `status: valid`, `invalid` or `abandoned`. An abandoned run (reading 10) prints its abandoned (sequence, seed) units and per-code cell counts, and no gates, hypotheses or reported block. A plan that leaves out a registered arm or set adds `design not fully run: <arms/sets> not planned` on the line after the status line.

**Determinism.** Scored records are sorted by (sequence, seed, position, arm), and bootstrap blocks by repository and family key, so the order of `--runs` and `--plan` files cannot change an estimate, a CI or a p-value.

**Inputs besides the records:**
- **Plan file** (`--plan`): the runner's `plan.json`, `[{ seed, position, arm, sequence, set, kind, familyId, taskId?, repo? }]`. It is G4's denominator and the declared design: the planned arms and sets come from it, never from the records. It must exist before any scored run. `set`, `kind` and `familyId` are required on every cell, under the record rules: `set` is R, N or X and the arm must belong to it; `kind` is teach, apply or no-lesson, with no-lesson only in set N; `familyId` is a string, and null exactly when the kind is no-lesson. A cell with any of the three absent is rejected with the missing field names and the cause: the plan came from a runner without the lesson-families fields. An empty plan is rejected. A cell listed twice, in one file or across several, is rejected with both locations. A record whose `set`, `kind`, `familyId` or `taskId` differs from its plan cell's is rejected. `repo` is kept but not checked, since E1 writes the clone URL there and records carry a short name.
- **Grading file** (`--grading`): `{ flippedLessons: string[], acceptanceFlips: integer, readerSample: { n, disagreements } }`. `acceptanceFlips` is reported only, since the prereg (166) sets no action for it.
- **Drop list** (`--drop-list`): `{ droppedLessons: string[], droppedFamilies: string[] }`.
- **Prices** (`--prices`): `{ "claude-code": Prices, "codex"?: Prices }`. H3 and H4 use Claude Code records only. Per-arm cost for set X shows as `n/a` unless `codex` prices are given.

The `--out` JSON holds everything the text holds, plus rotation slots and the memory-failure chain, which the text only points to. Every report lists the sha256 of each input file, the six analyzer modules, `src/eval-stats.ts` and `dist/eval-stats.js` (240).

## Record contract, `schema: "z0-record/1"`

One JSON line per (task, arm, seed). Unknown fields are allowed. A missing required field, a wrong type, or a field its kind forbids is rejected with the file and line number. Nothing is defaulted.

| field | type and nullability | prereg |
|---|---|---|
| `schema` | `"z0-record/1"` | |
| `set` | `R`, `N` or `X`; must match the plan cell's, as must `kind` and `familyId` | 46, 78, 85 |
| `tool` | `claude-code` or `codex`; set X teach records are `claude-code`, set X apply records `codex` | 85, 152 |
| `repo`, `sequence` | string; a sequence maps to one repo, and so does a `familyId`; sets R and N share sequences | 46, 117, 189 |
| `seed` | integer 1 to 3; 3 is rejected for A0, A4 and X4 | 122-124 |
| `arm` | `A0 A1 A2 A4 A5` in sets R and N, `X1 X2 X3 X4` in set X | 79-89 |
| `position`, `order` | integers >= 0: task index in the sequence, and E1's global step index. Position 0 is scored; E1's `scored` field is ignored | 117-120 |
| `taskId` | string; every arm runs the same task at a (sequence, seed, position), and it must match the plan cell's when the plan gives one | |
| `kind` | `teach`, `apply` or `no-lesson`; `no-lesson` only in set N | 39-46 |
| `familyId`, `lessonSource` | string and `maintainer` or `template` on teach and apply records, null on no-lesson | 39, 51-52 |
| `lessonId` | optional string on teach and apply records; informational, never read | |

| `acceptancePassed`, `timedOut` | booleans | 112, 165, 173 |

| `turns`, `toolCalls`, `fileReads`, `wallMs`, `teachTurns`, `correctionTurns` | integers >= 0 | 172, 175 |

**Invalid records.** A record with `invalid` set may carry null `usage`, work counts, `acceptancePassed`, `limitRetries` and `carryUnionMerges`, and may have empty `lessons`. Its `resolved` must be false, and is not compared with the resolved rule: E1 still runs the hidden tests after a crash, so `acceptancePassed` can be true on a record that never resolves. This matches E1's `skippedRecord` for `setup` and `leak` and its `no-result` record, and E2's invalid records. A setup failure ran no session, so E1 writes no retry or carry counts for it.

**One record per cell.** A second record for the same (sequence, seed, position, arm) is rejected with both locations, in one `--runs` file or across several. So is a record whose cell is not in any plan file.

**Cross-checks.** In each (sequence, seed, arm):
- an apply record's `tasksSinceTeach` must equal the number of positions after its family's latest teach record;
- each of its lessonIds must appear in a teach record of the same family.

Both checks are skipped when any planned teach cell of the family before the apply record, in its own (sequence, seed, arm), is missing or invalid. The plan names each cell's kind and family, so a missing cell is never guessed at. The skipped apply records are listed as `unchecked`, and the file is not rejected. A missing teach cell counts as missing in G4, and an invalid one as invalid. Scoring reads a narrower rule, the latest planned teach only (reading 18).

## Filters, in order

0. **G4 counts come first.** They are taken before any removal, so a void or a leak cannot hide a crash cluster. Per arm: planned cells, invalid records, missing cells, abandoned tail cells, and originating voids. A tail cell is never counted as missing.
1. **Drops.** Flipped and dropped lessons, and dropped families, are removed from every arm. Then `resolved` is recomputed.
2. **Abandoned runs.** An arm's abandoned tail in a (sequence, seed) is its planned cells after its last record there. Any tail makes the run abandoned (reading 10), and the (sequence, seed) is listed. Nothing after this step runs for an abandoned run.
3. **Unrestored retries.** A record with `limitRetries > 0` in any arm but A0 and A4, and without `surfaceRestored: true`, voids its position and every later position of its (sequence, seed), in every arm.
4. **G1 voids.** A voided cell removes that (sequence, seed, position) from every arm.
5. **G3 leaks.** A (sequence, seed) with any leak record is removed from every arm.
6. **Invalid records.** These are removed from scoring. Timeouts stay, and are scored unresolved.
7. **Untaught applies.** An apply position whose own arm's latest planned teach cell of the family before it is missing or invalid is removed from every arm, like a void, and counted as `untaught-apply drops` (reading 18).
8. **Pairing.** Seeds 1 and 2 only, when either arm is A0, A4 or X4. A task counts only when both arms have a scoreable record for it, and both records must carry the same `taskId`.

## Readings where the prereg is silent

1. H2 uses H1's two codings and `combineCodings`.
2. Attribution (148) is read only for a winning H1. With H1's final verdict a win, the lessons sentence needs A2 against A5 to have a CI high below zero under both codings; otherwise the "changed behaviour" sentence is printed. With H1 a tie, a loss or inconclusive, no sentence is printed, only `attribution: not applicable, H1 is <verdict>`, since both sentences in 148 describe an H1 effect. With A5 not planned and H1 a win, A2 cannot have beaten A5, so the "changed behaviour" sentence is printed with `A2 vs A5 not run`.
3. G1, a deliberate tightening: 161 voids a session in which an operator canary appears, but the analyzer fails the whole run on any operator canary, since a canary means the operator's own memory reached a session and the isolation itself is in doubt. A canary that only an apply's resume saw is in that record's `resumeVoidHits`, not its `void`, and still fails the run. Other voids drop their sessions, and per-arm void shares are printed beside the gate, since arm-differential voids are a selection risk the prereg sets no threshold for.
4. Holm runs once per coding over H1, H2 and H3, and then the two codings combine. When H2 is not run, its p enters as NaN, which ranks as 1, so the family size stays 3.
5. G2 is checked under both codings. "At least 30 points" is read as a point estimate at or below -0.30, with the CI's high below zero.
6. G1 and G3 voids remove the cell or the (sequence, seed) from every arm.
7. `resolved` is literal (173): acceptance passed, every lesson's final check is `pass` (an `na` is not a pass), and no timeout (165).
8. An unrestored retry in any arm but A0 and A4 voids its position and the rest of its (sequence, seed) in every arm, A0 and A4 included, until E3 records `surfaceRestored`. A0 and A4 are exempt only from starting a void, since their one carried surface is the instruction files E1 restores before a retry (114). Cut-offs fall more often on long sessions, so this removes costly tasks selectively. The report prints the voided share of positions beside H3.
9. `carryUnionMerges > 0` gives a sensitivity block. It is not an exclusion.
10. Abandoned is read literally from 114: "a run that stops partway is reported as abandoned and never analysed". Any abandoned tail, in any arm, gives the whole report `status: abandoned`. That is its own status: not invalid, and not a gate failure. The report lists the abandoned (sequence, seed) units and per-arm cell counts, and prints no gate verdicts and no hypotheses. Tail cells never count as missing in G4; a missing cell before an arm's last record still does.
11. An arm or set absent from the plan is "not run", never invalid, and the report says `design not fully run: <arms/sets> not planned`. Both lists are read from the plan only. The exception is G2: its Claude Code half is required whenever H1 or H3 runs, and its Codex half whenever H2 runs. A planned arm or set with no records is missing or abandoned data, never "not run": an arm with no records has its whole plan as a tail, so the run is abandoned.
12. **Invalid teach records (orchestrator amendment, 2026-10-03).** An invalid teach record counts like a missing one for the cross-checks: its dependent apply records skip both checks and are listed `unchecked`. In G4 it still counts as invalid, not missing. The optional top-level `lessonId` is accepted and never read.
13. A leak record may carry the same nulls as an invalid record, since E1 writes a leaked session through `skippedRecord` (`ab-run.mjs` 192).
14. A repeat-mistake unit is a (repo, family, seed) holding a scored apply record in either arm. One left with no paired task that has an applicable lesson in both arms is dropped and listed by name, whether a crash, a drop or the `excluded` coding emptied it.
15. Reported block:
    - Maintainer-only H3 keeps the no-lesson tasks, since they belong to no family.
    - The `tasksSinceTeach` buckets (198) report A2 minus A1 within each bucket, and each planned A-arm's own repeat-mistake rate per bucket under both codings, with units by (repo, family, seed). Each rate prints the seeds it read, since A0 and A4 run seeds 1 and 2 only (124).
    - The wordOverlap correlation uses one point per family: its A2-minus-A1 difference, averaged over seeds, against its mean `wordOverlap`. Families are the resampled blocks.
    - `followed` in the chain is read only where `shown` is true (181).
    - Rotation slots rank `order` among all records at a position, scored or not.
16. Blind output also lists abandoned runs, the locations of unchecked records, and warnings. None of these names an arm. An arm name inside a void reason is masked as `*` before the reasons are pooled. With fewer than two codes carrying voids, only the total is printed.
17. Any G5 failure refuses an unblind, "reader sample short" included, since 166 puts the second reading before unblinding.
18. **Untaught applies.** An apply record's relevant teach is the latest planned teach cell of its family before it in the same (sequence, seed, arm), read from the plan. When that cell's record is missing or invalid, the lesson was never taught in that arm, so its repeat-mistake check measures nothing. Its position is dropped from every arm, paired like a void, and the count is printed as `untaught-apply drops`. So a valid re-teach after a reversal keeps the applies after it even when the original teach crashed, and a teach position missing in every arm drops only its own family's applies. The cross-check skip (reading 12) is unchanged.
19. **Combining codings.** `combineCodings` gives loss when either coding is a loss, tie only when both are ties, win only when both are wins, and inconclusive otherwise. Prereg 138 fixes only the win rule; the loss and tie rules are the analyzer's, chosen so a harmful result under either coding is never hidden. H3 has no not-applicable case, so its two codings give one estimate, but Holm runs per coding (reading 4), so H3 can carry two adjusted p-values and two verdicts that then combine.
20. **H4 data.** H4 is "not run" when set N is absent from the plan. When set N was planned but missing records or the filters leave no paired no-lesson task, H4 fails with the reason `no set N data`, and the failure leads the report (146). Both 131 and 146 claim the lead, so the order is: any H1 to H3 loss, then a failed H4, then the other hypotheses and attribution. The losses go first because they are verdicts on the claims themselves; H4 then sits ahead of every non-loss.

**Tie note (136).** Win and loss are checked before tie. So when Holm inflates p, a CI that excludes zero but sits inside the band can come out as a tie. That is the prereg's order, and the analyzer keeps it.
