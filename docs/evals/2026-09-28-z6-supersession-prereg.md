# Z6 automatic supersession, shipped baseline: pre-registration

**Date:** 2026-09-28. **Status:** PRE-REG-LOCKED at the commit that adds this file, the fixture and the script. No scored run happens before that commit.

## Question

ROADMAP Part XV, Z6, test first: "a small update set (moves, preference flips, corrections, reversals) written in over normal prompts with no hippo commands, then asked across sessions. Pass means the current fact wins and the old one is retired with a reason, not merely ranked lower. Run it on hippo as shipped before building."

On hippo as shipped, when a user states a changed fact inside ordinary prompts, does the current fact win at a later question, with the old one retired and a reason shown? Where a scenario fails, at which stage does it first fail? The later Z6 build fixes stages in that order and is scored on the same held-out split (see the bar below).

**Pin.** Master `94a1f46`. The last commit to change `src/` is `e58ff49` (#297). `package.json` still reads 1.52.6; the 1.52.7 release being prepared changes no file under `src/` or `bin/`, so this is the 1.52.7 code. The draft was pinned to 1.52.4 (`4e85ac8`); every file:line below was re-read on the new pin, and the changes in between are listed at the end of (a).

## Mechanism claim (null expected)

Nothing on the shipped zero-touch path retires an old fact when a new one is stated. The expected pass rate is zero. The result that matters is the stage label per scenario.

The capture arm's labels are close to known before the run. Calling capture's own extraction (`summariseTranscript`, then `extractFromText`, the path at `src/capture.ts:861, 876`) on each of the 110 statement sessions, with no store, gives no item for 104 of them. Of the other 6, 5 give an item that holds the statement's marker. No change scenario gets both its old and its current statement stored. So the capture arm is predicted to label every change scenario `a` (not captured), which orders no stage after capture. The remember arm stores every statement, so it is the arm that orders the later stages.

## Data

- **Fixture:** `benchmarks/z6-supersession/fixture.json`, schema `z6-supersession-fixture/1`. Written by five Sonnet sub-agents in parallel parts (one per category, plus one for the controls and filler notes), none of which saw `src/`, so phrasing was not fitted to capture's cues. All invented, no real names or paths. Two authors were asked to replace three scenarios whose subject repeated another part's (commuting came up in three parts, a gym in two) and to reword four filler notes (three held another scenario's marker, one stated a fact about a control's subject). After the critique, the eval author edited two reversal questions by hand, dropping a final "now": they read "Which bundler builds the frontend?" and "What library handles state in the app?". hippo's tokenizer keeps "now", and in both it matched the old version's fact and not the current one. Ids are content hashes, so both ids changed, and the split, recomputed by the same rule, moved four reversal/coding scenarios: `z6-7316c4cb` and `z6-e79680bc` from tune to held-out, `z6-8b946ddc` and `z6-6bde2c89` from held-out to tune. No scored run and no held-out scenario had been run. Checked by `node scripts/z6-supersession-eval.mjs --selftest`.
- **Question reach:** each question shares at least one content word (hippo's own tokenizer, minus a fixed stopword list) with every statement's `fact` and with the user sentence that holds that statement's marker. Recall and explain are BM25 only here, so a question with no shared word could never reach its memories, and that miss would read as a supersession failure. No question contains `path`, `qa`, `qb`, `qc` or `proj`: `remember` tags every memory it writes with those path words (`src/cli.ts:993-997`) and BM25 indexes tags (`src/search.ts:464`), so such a question would match every remembered memory.
- **Change scenarios (40):** move, preference flip, correction and reversal (A, then B, then back to A), 10 each, 5 personal and 5 coding-project facts per category. Coding facts include npm to pnpm, a dev port change, a renamed test command, a new API base URL and a branch-naming rule.
- **Controls (10):** 5 restatements (the same fact twice, in different words; 3 personal, 2 coding) and 5 look-alikes (the same attribute about two different subjects; 2 personal, 3 coding).
- **Statement:** one session of 2 to 4 alternating turns. The fact sits inside an ordinary task prompt. `marker` is the value (a word or short phrase) that appears in the user turn; `fact` is a one-sentence version for the remember arm. No turn mentions hippo, memory or "remember that". The question never contains a marker; no marker appears in any background or interleave note.
- **Background:** 60 unrelated synthetic notes (personal and coding) written with `hippo remember` before any scenario, so "the newest five" is not trivially the answer. **Interleave:** 9 unrelated notes, 3 written after each statement.
- **Split, fixed in the fixture:** each scenario has an opaque id (`z6-` plus 8 hex of the SHA-256 of its content) and a `split`. Within each category and domain cell, a mulberry32 shuffle (seed 20260928 plus the cell index) picks the tune members: change cells alternate 3 and 2, so every category and every domain splits 10 and 10; controls split 5 and 5. **Tune 20 + 5 controls, held-out 20 + 5 controls.** The build tunes on `tune` only and is scored once on `heldout`. The id hashes `category`, `domain`, `statements`, `question` and `answer`, and the selftest recomputes every id and the whole split, so both can be checked from the repo.

## Procedure

`node scripts/z6-supersession-eval.mjs` runs everything and writes `benchmarks/z6-supersession/results.json` (ids, labels and counts only). Beside HEAD it records the last commit that changed `src/`, so a result stays tied to the hippo code it measured after the eval branch is rebased, and a SHA-256 over every file in `dist/`, which git ignores, so the built code is named too. A full run is all four arms; a run narrowed by `--only`, or by an `--arms` list that leaves out an arm, reports no verdict.

- **Isolation:** the store's folder must sit inside the system temp folder and outside any git work tree (checked with `git rev-parse`, under the same cleaned environment, once the folder exists), so the daily run's `learn --git` finds nothing. Hippo finds its store by walking up from the working folder and stops only at the home folder or the temp folder (`src/project-identity.ts:161-170`); the temp home here is not above the working folder, so from anywhere else under the user's home the walk would reach the user's real store. Right after `init`, before any write, the script checks that `init` created a new store in the working folder and that the workspace registry lists that folder alone. Every hippo call is `node <repo>/bin/hippo.js` with an argv array (no shell), HOME, USERPROFILE and HIPPO_HOME pointing at temp folders, `HIPPO_SKIP_AUTO_INTEGRATIONS=1`, and every variable whose name contains KEY, TOKEN or SECRET, every `HIPPO_*`, `CLAUDE*` and `GIT_*` variable, and XDG_DATA_HOME removed first, so no paid key (Anthropic, OpenAI, Voyage, Cohere, reranker) and no session or tenant override reaches hippo. A child process checks the keys are gone before the run starts. The script stops if an embedding package resolves from the repo's `dist/`: recall here is BM25 only, and nothing downloads a model. No hippo call gets `--help`.
- **Fixed path:** the store lives at `<tmp>/<base>/qa/qb/qc`, with the cwd at `.../proj`. The base is `hz6q` unless `--root-base` names another, so two runs can go side by side, but the last four cwd segments, from which `remember` makes its path tags, are always `qa`, `qb`, `qc` and `proj`. The tags are the same on every run and name nothing real.
- **Template:** `init --no-hooks --no-schedule --no-learn`, then `hook install claude-code`, then the 60 background notes at simulated days -40 to -1, with `hippo daily-runner` at 06:15 on days -39 to 0. Every daily run, here and in the arms, must end with "Daily maintenance complete: 1 workspace processed, 0 command failures." (`src/cli.ts:8309`): the runner exits 0 even when a child command fails, the registry is empty or the workspace has no store (`src/cli.ts:8285-8306`, `src/scheduler.ts:115`), so the exit code alone proves nothing. The script reads every hook command back from the temp `settings.json` and checks the set is exactly the seven in (a), by event, matcher and command, with SessionStart and SessionEnd naming the same log, and PreCompact and PostCompact naming the same log. It runs the three it replays with `hippo` swapped for the repo binary. Each scenario and arm starts from a fresh copy of the template.
- **Timeline** (`HIPPO_FAKE_NOW`, day 0 = 2026-09-01 09:00 UTC): statement k on day 5(k-1); three interleave notes on the next three days; the question on day 10 (day 15 for reversals). In the capture, remember and oracle-sleep arms, the interleave notes are written and `hippo daily-runner` runs at 06:15 on every day from 1 to the question day, as the installed schedule would; the oracle arm has neither. The script runs no other sleep.
- **Capture arm (primary):** each statement is one session. The script replays the installed SessionStart command, which clears the previous worker log, writes the session as a synthetic Claude Code transcript, and hands it to the installed SessionEnd command with the payload Claude Code sends (`session_id`, `transcript_path`, `cwd`, `hook_event_name`, `reason`). It checks the replay deleted the old log (`last-sleep` ignores a failed delete), waits for the worker's closing log line (`closed N active snapshot(s)`, or a no-session-id or close-failed line) and reads the capture outcome from the same log: "No actionable items found", or "Captured N items (M skipped as duplicates[, R rejected])". The worker runs detached with no output, so its log is the only failure signal: the log must also hold "[hippo] sleep complete" (`src/cli.ts:3125`), "[hippo] capture complete" (`src/capture.ts:742`) and exactly one outcome line.
- **Remember arm:** each statement is `hippo remember "<fact>"`; the daily runs do the rest. It separates "capture never stored it" from "supersession missed it".
- **Oracle arm (a check on the eval itself, change scenarios only):** statement 1 is remembered; each later statement is `hippo supersede <previous id> "<fact>"`, with no interleave notes, no sleep and no daily runs, so nothing but the explicit supersede acts on the pair. A scenario succeeds when it is labelled `d` or `d0` and `explain --include-superseded` lists at least one S and one C memory. That proves the labeller sees a retirement and the question reaches both versions, which the build's `d` depends on. Explain prints no reason on shipped code (see (a)), so `d0` is the expected oracle label. It is not a hippo result.
- **Oracle-sleep arm (reported only, change scenarios only):** the oracle arm with the interleave notes and the daily runs on. It shows whether a retirement, and the C memory it points to, outlive the daily runs. It is not part of the verdict or of the oracle check.
- **Ask,** in this order: the installed UserPromptSubmit command with the question as the prompt (a fresh session id), `hippo context --auto --budget 1500` (the block's task-start command), a plain `hippo recall "<question>"`, and `hippo explain "<question>" --include-superseded`. Then a read-only look at both databases: memories, `superseded_by`, confidence, tags, half-lives, `memory_conflicts`, the `forget` audit rows and the dormant table.

## Labels

**Attribution.** A memory created during statement k's step carries value k if it contains marker k as a whole word (case-insensitive), even if it also names the other value ("moved from Delhi to Mumbai" carries Mumbai). One created during step k with another statement's marker but not its own is an echo ("we moved out of X"): it carries no value and is counted. One with no marker carries nothing. A derived memory (content starting `[Consolidated`) carries the values of the earlier memories it quotes (it contains the first 60 characters of their text); one that quotes none carries the markers it contains and is flagged unlinked. A global copy carries its source's values. The stale value S is the second-to-last statement's; the current value C is the last one's (for a reversal, S = B and C = A, and only a statement-3 memory counts as capturing C).

**Surfaces.** Context: the injected text contains the memory's content, preceded by the label, date or warning prefix the renderer adds (`): `, `] ` or U+FE0F and a space) and followed by the closing `**`. The prefix matters: a merged memory ends with its longer member's text after a line break, and that tail must not credit the member. Auto: the `context --auto` output, matched the same way as context. Recall: the memory's id is in the ranked list. Recall returns every memory that shares a word with the question, within a 4,000-token budget, so on recall the rank decides. On a surface, the current fact wins when C is shown and S is not, or (recall) when C's best rank is above S's.

A carrier is **present** if it is still in `memories` (local or global) and **active** if present and not retired. Retired means any mark a shipped path writes: `superseded_by` set or kind `superseded` (supersede), tag `invalidated` (invalidate), tag `superseded` (`hippo decide --supersedes`, `src/cli.ts:5622-5632`), or confidence `stale`. Context and recall leave out only a `superseded_by` memory (see (a)), so only that mark can reach `d` or `d0`; a memory retired another way is still shown. Every label reports how many S carriers are retired (`sRetired`) and how many of those are still shown (`sRetiredShown`).

A retired S carrier is **linked** when its `superseded_by`, followed through every memory the script has seen, reaches a present C carrier, or when its own explain block (defined under `d`) matches the retirement pattern and names a C carrier id or the C marker. A retired S carrier with no link is counted. Explain drops a result whose first 200 characters (lowercased) match an earlier result, and local results come first (`src/shared.ts:300-307`). So a global copy of S whose local source is also returned gets no explain block of its own, and it can be linked only through `superseded_by`. A build that retires the global copy some other way must give it `superseded_by` too, or it scores `d0`. A retired S carrier whose `superseded_by` chain reaches no present memory at all is also counted as a dangling link: the memory it pointed to is gone.

First match wins:

1. `a` not captured: S or C was never stored (sub-counts: old, new or both, and the reason from the capture log: `no-cue` for "No actionable items"; `dup` when N = 0 and M > 0; `rejected` when N = 0, M = 0 and R > 0; `no-marker` when N > 0 but no new memory holds the marker; `not-stored` in the remember arm).
2. `x` removed: S or C was stored but has no present carrier at the question (sub-counts by value and by cause: dedup; other forget; merge-fade, meaning it went dormant with a half-life below the one it had when first seen, which in this run only a merge cuts; dormant otherwise; or unrecorded, meaning no audit row and not dormant; sleep deletes a faded memory that its secret check flags without writing one, `src/consolidate.ts:239-249`).
3. `d` retired with a reason (**pass**): every present S carrier, local and global, is retired and linked; C is shown on a surface, S on none; and explain gives a reason that links the two. Explain's detail block for a memory runs from its `[i] <id>` line to the next `[j] ` line or the closing `Note:` line; the table row is excluded because it prints content. The reason test passes when an S carrier's block matches `/supersed|invalidat|retired|replaced/i` and names a C carrier id or the C marker, or a C carrier's block matches the same pattern and names an S carrier id or the S marker. A bare status word is not a reason.
4. `d0` retired, no reason shown: S has no active carrier, C is shown on a surface and S on none, but the reason test or some link fails.
5. `s` stale only: S shown on a surface, C on none.
6. `n` neither shown.
7. `c` current wins but the old fact is still active: C shown, and the current fact wins on every surface that shows S.
8. `b` both returned, and the current fact does not win on some surface.

The brief's four stages map to `a`, `b`, `c` and `d`; `x`, `d0`, `s` and `n` are the cases those four do not cover. Per-surface labels (context alone, auto alone, recall alone) are reported beside the union label, which counts all three.

`d` checks the link and a retirement word only. ROADMAP's "Show it" also asks explain for the retired fact's date, source and rule; those are acceptance tests for the Z6 build, not for this eval.

**Controls.** A control is evaluable when every statement was stored; a restatement that capture skipped as a duplicate of its twin counts as stored. It fails when a carrier is retired and its `superseded_by` chain does not reach an active carrier of the same value (so superseding one restatement with the other is fine, and retiring either look-alike is not), or when a value that was stored has no carrier left (dedup keeping one copy of a restatement is fine). It passes when it is evaluable and nothing failed, and is `n/a` otherwise. Reported: pass, fail and `n/a` counts, and any open conflict rows between control memories.

**Filler guard.** Five held-out controls alone would let a rule that wrongly retires one fact in five pass about half the time. So in every scenario and arm, a background or interleave memory (exact fixture text, local or global) counts as a false retirement when it is retired at the question, or when the script saw it during the scenario and it is gone at the question (a build could retire by deleting). Lost filler is counted by cause. No background or interleave note reaches merge overlap (0.35) with another note or with any statement's `fact` (the highest are 0.250 and 0.158), so merges should leave filler alone, and with the default 365-day half-life (`src/memory.ts:491`) none should fade in the 55 simulated days. The counts and the number of active filler memories at each question, local and global copies together, are reported.

**Diagnostics.** Per scenario: an open conflict row between an S and a C carrier (the detector saw the pair); present derived memories by the version they carry, S only, C only or both (a pair merge keeps the longer text, so this shows which version outlived the pair); echoes; dedup deletions, whether the older or newer copy survived, and whether the survivor carries the deleted memory's value, the other value or neither; dangling links; retired S carriers and those still shown; and, under every label, the S and C carriers gone by the question, by cause, merge-fade included (a `c` can hide a carrier that dedup or dormancy removed). In every arm, the oracle's reach test (explain lists at least one S and one C memory) is recorded too: capture stores a clause of the sentence, so an `n` or `s` can come from the question not reaching that clause rather than from supersession.

## Metrics

Per arm and split: label counts, by category and by domain; per-surface labels (context, auto, recall); pass rate with a 95% Wilson interval; the number of scenarios where both S and C were stored (every label but `a`) and the pass rate among them, the build's second rate, so capture misses do not hide what supersession does; control pass, fail and `n/a` counts, the evaluable count and false conflict rows; filler memories retired, lost (by cause) and active; S and C carriers lost, by cause; derived, echo, dangling-link and retired-but-shown counts; unlinked retirements; oracle successes; reach counts. **Primary:** the capture arm on held-out. The remember arm on held-out orders the stages the build fixes.

## Z6 test-first bar (locked)

- Shipped **passes the bar** when the capture arm scores `d` on at least 18 of 20 held-out change scenarios, no held-out capture-arm control fails and at least 4 of the 5 pass, and no filler memory is retired or lost across the 25 held-out capture-arm runs. Otherwise it **fails**. The expected result is a fail at 0 of 20.
- `d` asks for less than the ROADMAP pass (see Labels), so this bar is a retirement check, not a Z6 pass. The Z6 build is scored on the same held-out split. Its own pre-registration, written before it is scored, must add the Show-it checks (the retired fact's date, source and rule in explain) and a run that writes the held-out scenarios into one shared store, gated on no scenario's memories being retired by another's. It may argue a different bar, before it is scored.

## Retraction conditions

The results are void, and no verdict is reported, when:

- a paid-API key or an embedding package is visible to a hippo call;
- the installed hook commands are not exactly the seven in (a);
- a SessionEnd worker does not finish within 60 seconds, or a hippo call exits non-zero unexpectedly;
- a capture log shows the script fed the session wrongly ("skip capture: no transcript", "No transcript found", "had no user/assistant messages", or "skip: no session_id");
- a capture log lacks "[hippo] sleep complete", "[hippo] capture complete" or exactly one capture outcome line (so "sleep failed", "capture failed" and "No text to capture from." void the run);
- a daily run's closing line is not "1 workspace processed, 0 command failures";
- the store's folder sits outside the temp folder or inside a git work tree, or `init` did not create a new store registered alone;
- the oracle arm (not oracle-sleep) succeeds on fewer than 36 of 40 change scenarios (the labeller or the questions cannot see a retirement);
- a second full run reaches a different verdict.

Per-scenario label changes between the two runs are reported, not voiding: memories written at one `HIPPO_FAKE_NOW` share one `created` millisecond (the worker's sleep output and its capture; everything one daily run writes), and the recent-N list breaks that tie by random id (`src/api.ts:2777-2790`), so which of a statement's memories reach the five newest can differ.

## Disclosures

- The transcripts are short and model-written; real users bury facts in longer sessions and state them less cleanly. Results are reported per category so a phrasing effect shows.
- The union covers three surfaces. The context hook shows the five newest memories, so its result depends on how many memories land after the last statement (three interleave notes, that statement's own, and any the daily runs write). `context --auto`, with no git repo to build a query from, shows the strongest memories that fit 1,500 tokens; among fresh memories of similar strength that choice is close to arbitrary. It also marks what it shows as retrieved, and it runs before recall, so recall sees those memories a little stronger; the order is fixed. Recall stands for an agent that chooses to search: the block hippo writes never tells it to. The union label is primary, and each surface's label is reported.
- Question words and marker sentences: 16 of the 40 change questions share a word with one version's marker sentence and not the other's, 8 leaning each way (held-out: 6 toward the old version, 3 toward the current one). On the `fact` texts the remember arm stores, none does. This can move recall rank for captured clauses only.
- Out of scope: what the SessionStart hook shows the agent (the previous worker's log, merge previews included), and the four hooks that fire only around a compaction or after a failed tool call (pre-compact, compact-resume, post-compact and capture-error).
- An unshipped capture extractor candidate (`docs/evals/2026-09-28-z0-session-capture-v2-prereg.md`) is out of scope: this is the shipped path only.
- `learn --git` can invalidate memories named in a commit message (`src/cli.ts:7496`). No scenario makes a commit, since Z6 is about facts stated in prompts, so that path is not exercised.

## Critique

An independent reviewer read the draft pre-registration, script and fixture before the lock, with the trace of the first pre-lock run. It returned 15 findings: 1 blocker, 10 should-fix and 4 nits. 12 were applied in full and 3 in part; each rejected part carries its reason.

1. **Blocker.** Merge cuts the half-lives of both members of a pair again at every sleep, so in the remember arm the raw memories fade and one derived memory keeps one version's text. Applied: a merge-fade cause, derived S, C and both counts, and (a), Labels and the filler guard corrected.
2. The capture result was known before the run. Applied: the prediction is in the mechanism claim, the remember arm orders the stages, and the pass rate among scenarios with both versions stored is reported.
3. A control passed when nothing was stored. Applied: it passes only when every statement was stored, is `n/a` otherwise, and the bar needs 4 of 5 held-out passes.
4. `d` needs the C memory to outlive sleep, which the oracle never tests. Applied in part: dangling links are counted and the oracle-sleep arm is added. Rejected: counting a link that ends at a C memory which is gone, because a gone memory cannot back the current fact on any surface; a reason that names the C marker still links.
5. Only `superseded_by` can reach `d`. Applied: stated in (a) and Labels, and retired-but-shown S carriers are counted under every label.
6. Recall is not a surface the zero-touch path produces. Applied: `context --auto` is a third surface in the union, and recall is declared as an agent that chooses to search.
7. A same-value supersede failed a restate control. Applied: a retired carrier is fine when its chain reaches an active carrier of the same value.
8. The filler guard cannot see a wrong retirement of a related fact, and its cap was wrong. Applied in part: the cap is gone and the overlap probe is stated. Rejected for this eval: a shared-store run, because shipped hippo writes no automatic retirement for it to catch; the build's pre-registration must add it (see the bar).
9. `d` is weaker than the ROADMAP pass. Applied: the rule is renamed the Z6 test-first bar, and the build's pre-registration must add the Show-it checks.
10. The hook check let other hooks through. Applied: the script checks all seven commands exactly and stops otherwise.
11. Held-out labels are published per scenario, and the split could not be recomputed. Applied in part: the selftest recomputes every id and the split from content, which replaces the one-off assignment script. Rejected: holding back held-out labels, because the per-scenario stage label is this eval's main output and the fixture and script are public anyway; the build is held to the split by its own pre-registration.
12. Echo clauses counted as S carriers. Applied: echoes carry no value and are counted.
13. Dedup deletions recorded only the survivor's age. Applied: they record the value relation too.
14. Two reversal questions shared "now" with the old fact only. Applied: "now" dropped, ids and split recomputed (see Data).
15. `dist/` and the git environment were not pinned. Applied: results carry a hash of `dist/`, and `GIT_*` variables are removed.
