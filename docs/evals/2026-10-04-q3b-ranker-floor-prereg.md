# Q3b ranker floor check: pre-registration

**Date:** 2026-10-04. **Status:** LOCKED by the commit that adds this file. No arm was scored before the lock, and the harness that scores them is not written yet. Nothing was run for this doc.

Audit row Q3b: "Merging rankers must move two of them... winner picked on the retrieval eval, snapshots updated, changelog entry." The recall surfaces and how they differ today are listed in [../recall-surface-differences.md](../recall-surface-differences.md).

## What this is, and what it is not

This is a **retrieval-floor check**. It picks which of today's three ranking cores the single recall entry point keeps, and it guards against the merge dropping answers the micro-eval already finds. It is **not a success measure** for hippo: a higher pass count here says nothing about whether agents do better work. Outcome benchmarks answer that question, and this result must not be quoted as one.

## Question

CLI `hippo recall`, MCP `hippo_recall` and HTTP `GET /v1/memories` each rank with a different core. After the merge one core ranks for all three. Which core keeps the most micro-eval passes, and does any core lose answers that sit beyond row 200 of the BM25 order?

## Arms

All three arms run in one TypeScript harness, in process, through `retrieve()` (`src/api/recall.ts`) on a real store. Only the ranking core differs. Every post-ranking stage a query asks for (goal boost, salience threshold, value-aware, utility rerank, EVC, conflict filter, cross-encoder reranker, include-superseded) runs the same way on every arm, as one shared stage list in the request.

| Arm | Ranking core | Candidate load | Score |
|---|---|---|---|
| A, CLI core | `rankRecall`'s search step (`src/recall-pipeline.ts`): physics or hybrid search per the store config | 200 rows per store, additive scope mode | the engine's score |
| B, HTTP SQL BM25 | the SQL BM25 load order, then the churn sort (`retrieve` without `mode`, `src/api/recall.ts`) | 200 rows, exact scope mode | list position, `1 - idx / limit` |
| C, MCP showRanked | the `showRanked` path (`retrieveFromStore`): physics or hybrid search per the store config, goal boost once | at least 1,000 rows, exact scope mode | the engine's score |

The store config is the default `hippo init` writes. If an arm cannot run a stage a query asks for when the harness is built, that query counts as a fail for that arm, and the result names each such query.

## Corpus

1. **Micro fixtures:** `benchmarks/micro/fixtures/`, 13 fixtures and 33 queries, unchanged. Each fixture store is built with the built CLI, using the same commands in the same order as `benchmarks/micro/run.py`: `init`, `remember`, then the fixture's actions. Each query then runs once per arm from its `cwd_subdir`, in a fresh copy of the store. Pass and fail follow `run.py`: at least one `must_contain_any` string in the top `top_k`, and no `must_not_contain_any` string there.
2. **Window fixture:** one new fixture of 1,600 memories, generated by a seeded script committed with the harness and before any run. It holds 600 strong filler rows that contain the query terms twice, 990 weak filler rows that contain them once in longer text, and 10 short target rows that contain them once. Each target then sits between row 201 and row 1,000 of the BM25 order: outside a 200-row window, inside a 1,000-row one. The generator checks that placement and fails if any target falls outside it. Two targets are pinned, two carry the tag of an active goal (the query passes `--session-id`), one has three positive outcomes, and five have no lift. The 5 queries each name one lifted target, and a query passes when its target is in the top 5. The five unlifted targets are controls: they must not appear in any arm's top 5, and if they do the fixture is broken and is fixed before the run.

The total is 38 queries.

**Calibration caveat, stated before the run:** the micro fixtures were written and tuned against the CLI core (see the comment in `benchmarks/micro/run.py`, `preflight_embeddings`), so arm A has a home advantage on corpus 1. The window fixture is new and favours no arm by construction.

**Embeddings:** every arm runs with the Transformers.js backend installed (`npm install --no-save @huggingface/transformers@4.2.0`), and `run.py`'s preflight must pass first. A BM25-only run is not a result.

## Metric

The **pass count** over the 38 queries, per arm.

Latency is per-query `retrieve()` wall time, in process, on the window fixture: 3 warm-up runs, then 30 timed runs per query. The **p99** is taken over all 150 timed runs per arm.

## Decision rule (locked)

1. An arm **wins** if its pass count is at least **2 queries** higher than every other arm's.
2. If no arm wins by that margin, the arm with the **lower p99** wins.
3. The result reports every arm's pass count, its p99, and each query where the arms disagree.

The winning core becomes the one ranker. The goldens in `tests/recall-surface-parity-golden.test.ts` and `tests/cli-recall-golden.test.ts` are then updated in the same PR, and the changelog lists every visible change one line per surface.
