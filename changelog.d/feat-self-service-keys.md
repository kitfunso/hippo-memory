### Added

- **`hippo-memory/server` exports `authCreateSelf`, with the `AuthCreateSelfOpts` and `AuthCreateSelfResult` types.** An add-on route calls it to mint the signed-in caller its own member key. Only a caller verified by the `authResolver` may use it; an `hk_` API key or the local CLI gets `ForbiddenError`. The key is always `member`, its tenant and owner come from the verified identity, and it expires after `ttlDays` (above 0, at most 3650). Past `perSubject` live keys (a whole number, at least 1), the oldest are revoked in the same transaction. Each replaced key gets an `auth_revoke` audit row and the new key an `auth_create` row with `self: true` and `expiresAt`; if any audit write fails, no key is minted and none is revoked. A bad `ttlDays` or `perSubject` throws a `RangeError` before the store opens.
- **A member signed in through the auth resolver can revoke the keys it minted for itself.** `DELETE /v1/auth/keys/:keyId` and `authRevoke` accept a key whose owner is the caller, in the caller's tenant, and write an `auth_revoke` audit row. Another member's key, a member key an admin minted and a missing key all get the same 403, so key ids cannot be probed.
- **API key lists carry `expiresAt` and `ownerSubject`.** Both are null for a key that never expires or that an admin or the CLI minted. `hippo auth list` shows an `expires` column.
- **`scripts/check-expiring-keys-floor.mjs` checks the binary floor for expiring keys.** It runs on `npm version`, `prepublishOnly` and CI, and fails when `EXPIRING_KEYS_MIN_BINARY` is above the package version or names a tagged release that does not ship schema v53.

### Changed

- **Schema v53 gives API keys an owner and an expiry; the first expiring key makes older binaries refuse the store.** `api_keys` gains nullable `owner_subject` and `expires_at`; keys minted before v53 or by an admin keep both null and never expire. An expired key gets 401 on every route, MCP and the event stream included, and a cached key stops at its expiry, not a cache TTL later. The migration leaves `min_compatible_binary` alone, so a store with no expiring key still opens in older binaries. The first self-minted key raises it to `EXPIRING_KEYS_MIN_BINARY`, the first release with v53, in the same transaction as the key, because an older binary would ignore `expires_at` and keep honouring expired keys. Upgrade every hippo binary that shares a store before anyone mints a self-service key. To undo it, revoke every key that has an expiry, then lower the floor (see `docs/ARCHITECTURE.md`).
- **Active key lists leave out expired keys.** `GET /v1/auth/keys` (active by default), `authList` with `active` and `hippo auth list` drop a key once its expiry passes; `?active=false` and `--all` still show it.
- **A member listing `GET /v1/auth/keys` sees only their own keys.** A member signed in through the auth resolver sees the keys they minted; a member API key sees the keys of the person who minted it, or just itself when it has no owner. Admins still see the whole tenant.
- **A key mint by an admin signed in through the auth resolver fails when its audit row cannot be written.** The key and its `auth_create` row commit together, since that row is how the key is traced back to who minted it. Other admin mints, the local CLI included, are unchanged: the key is kept and the failed audit write is reported.
- **`POST /v1/auth/keys` now reads its body before it checks auth, capped at 4 KB and 10 seconds.** Auth, including any deactivation check inside the resolver, now runs right before the mint, so a user deactivated while the body was in flight gets no key. A larger body gets 413. A body that has not arrived within 10 seconds gets 408 and the connection is closed, so a caller with no credential cannot hold a socket open by trickling bytes.
