### Fixed

- **Promote on a shared store (a team `hippo serve`, or `hippo promote` in a shared folder) now copies nothing.** Every member whose project admits the row already reads it there, so a copy only added a duplicate that the next sleep's dedupe deleted. Promote checks the row as before, writes a `promote` audit row and answers `{ ok: true, sourceId, globalId, originProject }` with `globalId` equal to `sourceId` and `originProject` the row's project (`''` for a user-global row, `null` for a row with no project). A member sends its project in the body (`{"project": {"name": ...}}`): a row outside that project answers as a missing id, and a call with no project gets 400. A host admin (the CLI on the folder, stdio MCP, or an admin key in the server's own tenant) needs none. With `hippo serve` running on a shared folder, `hippo promote` sends that folder's project, so a row of another project reads as not found. A row with no project (the CLI's own rows) also reads as not found, and so does a row stamped with the legacy folder name, since the route reads only the project's name and aliases. Set `HIPPO_API_KEY` to a host admin key or stop the server to promote those. There is no copy to outlive a forget or archive: a forget removes the row for every reader. On a shared SQLite server promote no longer writes a copy into the server operator's own global store under HIPPO_HOME. On every store, the laptop included, promote now refuses a superseded memory with 409 and names the memory that replaced it.
