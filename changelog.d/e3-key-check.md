### Fixed

- **A revoked API key stops working on the very next request.** `hippo serve` used to trust a key it had checked for up to 60 seconds, so a revoke, an expiry, a role change or a scope grant made by the CLI or another server process landed up to a minute late. The server now reads the key's row on every request and remembers only that a secret matched its stored hash. A valid key gets the same answer as before; each authenticated request costs one extra indexed read.
- **Checking an API key no longer holds up other callers.** The key hash is derived on the thread pool, at most two at a time with eight waiting, so the server keeps answering while a key is checked. A key the server has already checked since it started is not derived again.
- **One address gets five tries at one key id, then one more every 12 seconds.** Past that, a key check from that address for that key id answers `429` with `{"error":"too many key checks from this address"}` and `Retry-After: 12`, and no hash is derived. Other addresses, other keys and a key the server has already checked are not affected.
- **A key check that finds two derivations running and eight waiting answers `429` with `{"error":"rate limit exceeded"}` and `Retry-After: 1`.** This can reach a real caller when more than ten keys are checked for the first time at the same moment, for example right after a restart; a retry one second later passes.
