### Added

- **`serve()` takes a `routes` option, so an add-on can mount its own POST `/v1` routes.** Each route is `{ path, handler }`. Core checks the API key and parses the JSON body, then sends the handler's return value as a 200 JSON reply; an `HttpError` the handler throws becomes that status with an `{"error"}` body, and a status outside 100-999 becomes a 500. `serve()` refuses to start on a path that is not a plain `/v1/` path, is listed twice, or is already served by a core POST route or a public connector webhook, so an add-on cannot shadow a core route. Under a store other than `hippo.db`, an add-on route answers 501 after the auth check, like any route not yet ported. `GET` add-on routes, query strings and routes that run before the store is ready are not part of this seam.
- **`hippo-memory/server` exports `promptHookContext`, `HttpError` and the types `AddonRoute`, `AddonCall` and `JsonValue`.** `promptHookContext(ctx, { sessionId, project, payload })` returns the text `hippo context --pinned-only --include-recent 5 --format additional-context` would print for that session in that project, read from the store behind `ctx`, with the holdout arm and the token ledger rows (inject, prompt recall and skip) booked there under the session id and `ctx`'s tenant. A holdout session gets an empty `stdout`; `arm` is the ledger's `hippo` or `holdout`, or `null` when the store's holdout rate is 0. Scope detection (`HIPPO_SCOPE` and the skill variables) and delivery-ledger events stay with the CLI. The session id and each project name may be at most 256 characters, and a project may carry at most 10 aliases; past either cap the call throws `BadRequestError`, which an add-on route answers as a 400. A route uses it to answer a prompt hook that runs on another machine.
- **`promptHookContext` takes `{ sharedStore: true }` as a third argument, for a store that serves many people.** The caller is then not treated as the store's owner. Recent rows come only from the caller's project names, so user-global recent rows are left out; pinned rows are unchanged. The global store of the user running the server is not read. The task snapshot, handoff and session events appear only when the snapshot belongs to the caller's session. When the served folder has no `hippo.db`, no ledger or arm rows are written anywhere. Without the option the result matches the local hook.
- **`hippo-memory/project-identity` exports `resolveProjectIdentity`,** so a hook client can name the project it runs in the same way the local hook does. The subpath exports only `resolveProjectIdentity` and its two types.
- **`hippo-memory/json-hooks` exports the Claude Code hook installer,** so a client that replaces hippo's local hooks removes them with the same code `hippo init` adds them with. The subpath exports `installJsonHooks`, `uninstallJsonHooks`, `resolveJsonHookPaths` and their result types.

### Changed

- **Context finds a project's recent rows without reading the whole store when the newest rows belong to other projects.** When the newest window holds too few of the caller's rows, the next read asks SQL for the caller's projects only, instead of loading every row. The rows returned are the same.
