### Security

- **A member key acts by id only on rows it may read.** The writes by id checked only that a row was not someone else's personal one, so a member key with no grant could delete or archive a row in a restricted `<source>:private:` scope, and a 200 against a 404 told it which ids existed. Each now applies recall's read rule, grants included: delete, archive, pin, supersede and outcome inside the write's own transaction, and promote, reject, MCP share and conflict resolution before they act. Such a row answers 404 word for word as a missing id. Admin keys see no change. A store built on `store-kit` reads `role` and `grants` on `EntryTarget` and checks them with `readerReaches`; see `docs/UPGRADING-3.0.md`.
- **One key id cannot fill the key-check queue.** Key ids are not secret, so wrong secrets for one key id sent from many addresses could hold both scrypt slots and all eight waits, and every other key's first use got a 429. A key id now holds at most one derivation and two waits; past that only that key id answers 429.
- **The previous GitHub webhook secret can expire.** Set `GITHUB_WEBHOOK_SECRET_PREVIOUS_UNTIL` as `SLACK_SIGNING_SECRET_PREVIOUS_UNTIL` is set; from then on a delivery signed with the previous secret gets a 401, at the webhook and in `hippo github dlq replay`. A previous secret of either connector with no end date keeps working, and the server warns once at start, naming the variable.
- **The dashboard session cookie carries `Secure` when its request came over TLS.**
- **An IPv6 client is rate limited on its /48, not its /64.** One /48 holds 65,536 /64s, so a client rotating through them got a fresh bucket each time and pushed other clients' buckets out of the table. Every /64 of a /48 now shares one bucket.
