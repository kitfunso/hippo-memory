### Security

- **`hippo serve` now refuses a request with no API key, from this machine too.** A request from the same machine used to be let in with no key and act as host admin, so any local process, and any other container in the same pod, could read, write and administer the store. Now every request needs a key unless the server is started with `HIPPO_ALLOW_KEYLESS_LOCAL=1`. `HIPPO_REQUIRE_AUTH=1` works as before and wins when both are set. The refusal is a `401` whose text names both fixes, and `hippo serve` prints the rule it is running under at every start.
- **`GET /health` gives its version and process id only to a caller on this machine.** A page in a browser that reaches the server through another site, or through a hostile name that resolves to `127.0.0.1`, now reads `{"ok":true}` and nothing else, as a caller from another machine already did. This check does not depend on the key rule.
- **Upgrading.** Nothing changes if you never run `hippo serve`, if your callers already send a key, or if the server runs with `HIPPO_REQUIRE_AUTH=1` (the Docker image in `deploy/aml` does). If you run `hippo serve` and call it with no key, those calls now get `401 auth required: this server takes no request without an API key...`. That covers `curl`, the Python client built with no `api_key`, an MCP client aimed at `/mcp` with no `Authorization` header, and the CLI itself: while a server runs for a store, `hippo remember`, `hippo forget` and `hippo promote` in that store go through it, so they print `Error: auth required: ...` and exit non-zero, and so does any hook or script that calls them. The one step that restores the old behaviour is to restart the server with `HIPPO_ALLOW_KEYLESS_LOCAL=1`. The better step is a key: run `hippo auth create` on the host (it needs no key and no server), then set `HIPPO_API_KEY` for the CLI, pass `api_key=` to the Python client, or send `Authorization: Bearer <key>`.
