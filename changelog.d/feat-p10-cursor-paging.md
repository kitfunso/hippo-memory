### Changed

- **The `/v1` list routes page with a cursor, and the two that had no bound now have one.** `GET /v1/auth/keys` returns at most 1,000 keys per request, where it used to return every key, and `GET /v1/quarantine` takes a `limit` (default 100, as before; at most 1,000). A deployment under those sizes sees the same response as before.
- **Every list route takes optional `cursor` and `limit` params and says where the next page starts.** `/v1/decisions`, `/v1/incidents`, `/v1/processes`, `/v1/policies`, `/v1/skills`, `/v1/project-briefs`, `/v1/customer-notes`, `/v1/predictions` and `/v1/quarantine` add `next_cursor` as the last body field: pass it back as `?cursor=` for the next page, and it is `null` on the last page. `/v1/auth/keys` and `/v1/audit` return a bare JSON array, so their next cursor is the `X-Next-Cursor` response header, absent on the last page. Pages are ordered newest first with ties broken by id, so a row written while a client pages never shifts a page or repeats a row. A cursor the server did not mint is a 400 in the usual `{ "error": ... }` shape. Default limits and existing fields are unchanged.
- **The Python SDK's `auth_list` follows `X-Next-Cursor`,** so it still returns every key past the new 1,000-key page, and takes an optional `page_size`.
- **CI runs the p99 recall benchmark at 1,000 memories** on every pull request, so a recall latency regression fails a PR before release.
